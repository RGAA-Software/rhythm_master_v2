# 当前完成度与后续实施路径

更新日期：2026-09-11。本文是 Rhythm Master 当前执行状态的统一入口，具体功能合同仍以
各专项文档为准。历史文档中的 Basic 50 + Advanced 50 已被最新产品决定替代：产品目录
只保留高端、可编辑的 Advanced 作品，当前目标为 **50 个独立验收的 Advanced 模板**。

## 1. 完成度口径

完成度不是测试通过率，也不按节点、模板或提交数量计算。下面的区间综合功能合同、真实
作者路径、实际 GPU 输出、目标平台、视觉品质和最终交付六类证据，用于安排工作量，
不是统计承诺或完成日期。

| 范围 | 当前估计 | 已具备 | 尚未闭环 |
| --- | ---: | --- | --- |
| 底层架构与核心功能 | 约 80% | 图编译/运行、节点预览、音频特征、时间/事件、组件、2D/3D、粒子、物理、媒体、保存发布、Player 和导出主干 | 若干核心画质算法、高质量档、复杂边界和统一动态评审 |
| Windows Studio/Player | 约 75% | 从零创作、模板应用、保存重开、发布、运行包、有声导出和强制 delivery 回归 | 大图性能收口、完整演出组合、作品批量画质验收和最终一致性报告 |
| Windows + Android 主线 | 约 60%–65% | Android Player、内置选择、真实 PCM/GLES 多批短验证、覆盖安装和方向基础 | 当前内容对应 APK、系统音频/焦点、权限、前后台、资源重建、档位和最终实机矩阵 |
| 含内容、P9、Apple、通信的完整规划 | 约 45%–50% | 共享核心与两端主干已经成形 | 50 个合格 Advanced、最终长稳/发行、Apple 移植、最后通信，以及待定透明原生输出 |

剩余主线约 35%–40%，但工作量集中在画质、作品制作、动态观察和实机验收，不能按剩余
代码行推断耗时。

## 2. 当前可靠基线

- P0–P6 的主要产品合同已有实现和专项证据；量化节拍、本地事件、演出列表、音画切场、
  视图直接编辑、文字/矢量/数据桥接及受限 Shader/GPU 属性能力均有可运行路径。
- Windows delivery 当前为 9/9，通过实际 Studio 模板应用、节点 ID 重映射、当前输出、
  保存重开、发布、双语 GPU 与大型音乐工程。Studio/Player deploy 各含最新程序、20 个
  DLL 和完整资源。
- 普通 blur 已换为 Godot Gaussian；glow 使用 Godot dual filtering；Reinhard、Filmic、
  ACES、AgX 和五种 glow/display 合成顺序已有 D3D11 像素回归；透明排序、显式 priority、
  sorting offset 和 alpha depth prepass 已交付。
- Circular DOF 已采用 Godot 有符号近远 CoC 与边界遮挡，但完整 bokeh 质量档仍未完成。
- 已提交内容库存为 **21 个 Advanced 候选、40 个组件、235 条预设记录**；其中 132 条
  默认值记录，以及重复设置和未审项目不能计入 120 个独立合格预设。
- 品质账本仍为 **0 个完全闭环模板**。这不否定已通过的功能和音乐证据，只表示尚未同时
  完成 functional、music、visual、device 四阶段并绑定当前源码身份。

## 3. 实施顺序

当前阶段遵循用户最新决定，只处理 Windows。每个增量先完成受影响目标、实际 D3D11
检查和必要 Studio 路径，再进入下一模块；不提前做长稳，不恢复通信，不开发 Apple。

### W1：核心画质收口

| 顺序 | 工作 | 实施路径 | 退出条件 |
| --- | --- | --- | --- |
| W1.1 | 阴影质量 | 固定 Godot 源码；保留 Nearest/PCF5，增加 PCF13；随后验证方向光稳定投影/级联与点光阴影的实际作品收益和成本 | 大投影、移动相机、细几何的 D3D11 像素与短性能证据；旧作品默认行为兼容 |
| W1.2 | 完整景深 | 在已交付 circular CoC 上增加 Godot Box/Hex、quality/half-size、独立权重和最终 composite | 近景细线、远景高光、透明边缘、横竖屏和动态相机无明显背景泄漏；资源与 pass 预算明确 |
| W1.3 | 环境与材质 | 对照 Godot reflection/environment filter，改进粗糙度 LOD、采样分布和能量一致性 | 固定 HDR 环境的金属/粗糙度阶梯回读与作品动态对照 |
| W1.4 | 粒子呈现 | 增加纹理图集、形态/材质变化、软深度交界和分层体积感；保留现有 GPU 模拟合同 | 大小粒子边缘自然、无硬块/重影；低中高频分工和静音自主运动均可观察 |
| W1.5 | 时域与程序纹理 | 修复 trail/feedback 快速运动及回收边界；增加 domain warp/多频谱噪声；评估移动细线的 TAA/MSAA/FSR 路径 | 连续多周期无跳变；采用项有固定来源、短成本和实际作品收益，未采用项有明确结论 |

W1 不要求一次嵌入整个 Godot。每项采用聚焦算法，保持项目公共句柄、所有权、bgfx 后端
和 Windows D3D11 契约；来源、revision、哈希、许可及修改写入 `provenance/`。

### W2：现有作品统一升级与品质标尺

先处理 21 个已提交 Advanced 候选，不盲目把局部 glow 与最终 display 合并。逐图确认旧
blur 的真实用途、HDR 阶段、透明边缘、粒子层次和性能，再决定结构迁移。

每件作品必须同时满足：

1. 静音时存在持续流动、旋转、前进或空间相机运动，普通循环无回跳和喷发停顿。
2. 音乐调制既有运动；低、中、高频及响度分配到可辨识的不同元素和时间尺度。
3. 粒子、物理、3D、材质、glow 等按构图需要使用，不机械地给所有作品套同一种技术。
4. 节点连线完整、分类清楚、关键节点有实时预览；公开控件在上下限仍保持可用画面。
5. 实际 Studio 应用模板后验证当前输出、保存重开、发布、Player 和适用的有声导出。

先用 4 件代表作冻结视觉标尺，再按每批 5 件复核。失败先修同类共享节点，避免在每个
模板中堆特例。审核写入 `content_reviews.json`，源码变化使对应旧审核失效。

### W3：扩展到 50 个合格 Advanced

- 当前 21 个候选全部复核后，按文化、空间、抽象、字体/矢量、粒子/物理和三维雕塑等
  系列补足至少 29 个独立候选。
- 每个新作品先制作概念动态图或参考板，再实现可编辑图；复刻开源/公开展示时记录来源，
  核心效果优先使用已固定的 Godot 算法。
- 换色、横竖屏副本、同图参数变化和节点堆叠不增加独立数量。
- 40 个组件候选已达到数量目标，后续以作品实际复用缺口和品质审核为主。
- 预设执行去重和独立性审核，目标是 120 个视觉上独立且有实际用途的合格预设。

### W4：Windows 产品闭环

依次完成从零创作、模板修改交付、连续演出和性能报告。代表性小/中/大图分别记录 Studio
开启/关闭节点预览、Player 和导出条件下的 CPU 阶段、可取得的 GPU 数据、纹理内存、
p50/p95 和峰值。不得以降低已接受画质作为唯一优化，也不得用任务管理器 GPU 百分比
替代计时。

Windows 退出条件是同一当前源码和内容版本通过：完整作者操作、节点/最终预览、真实系统
或文件音频、列表/量化/切场、保存发布、Player、窗口/全屏和有声导出；失败能定位到具体
阶段并保留日志。

### A1：Android 最终主线

Windows 当前批次冻结后，再构建当前 runtime-content 与 APK，核对包内哈希并使用
`adb install -r` 覆盖安装。通过应用内置 UI 选择作品，验证真实系统音频/文件音乐、
公开控件、队列、横竖屏、音频焦点、权限、前后台和 GPU 资源重建。只声明当前实机和
明确质量档，不从一台 Adreno 650 推断全部 Android 设备。

### R1：最终长稳与发行

功能和内容错误先修完，再冻结候选版本执行 Windows Studio/Player 与 Android 的长稳、
热状态、内存趋势、音画漂移、循环、切场和恢复矩阵。随后整理 Windows deploy、APK、
源码提交、依赖/许可、内容清单、能力矩阵和已知限制。

### L1：最后阶段

1. 获得 Apple 工具链和设备后，依次完成 macOS 共享核心/Metal、Studio/Player、字体/IME/
   音频/导出，再完成 iOS Player、权限、生命周期、签名和实机验收。
2. 主线完成后重新盘点已有通信试验，收敛最小控制、时间和输入快照；不默认沿用复杂协议。
3. 透明原生后缓冲/窗口合成保持待定，仅在仍有明确产品用途时验证；不恢复壁纸设计。

## 4. 每个增量的强制检查

- 修改核心效果前先查本地固定上游，记录复用与兼容缺口；依赖优先 `C:/source/vcpkg`。
- 增量构建使用 20 workers，不清缓存；新工具使用 Python。
- GPU/UI 检查只通过 `tools/verify_windows.py`，Studio delivery 只通过
  `tools/build-windows.py`，并保留每次成功和失败日志。
- 每次 Studio 交付都验证模板实际应用、ID/宏/快照/Cue 引用、当前输出、保存重开和发布；
  构建后自动刷新与 exe 同级的 deploy 目录和全部 DLL/资源。
- 动态作品检查静音、真实音乐、多个连续周期和回收边界；截图及非零像素差不能证明运动品质。
- 当前只提交本增量相关文件；未完成的独立作品工作树不混入提交。

## 5. 状态更新规则

每项使用“未开始 → 合同/验证中 → 实现中 → 集成检查 → 已交付”，另列视觉与平台状态。
只有所有退出条件都有当前源码对应证据才提高完成度。候选库存增长只更新 authored 数；
通过四阶段审核才更新 accepted 数。发现用户可见错误时暂停当前工作包，先复现、记录、修复
并加入永久检查，再恢复队列。
