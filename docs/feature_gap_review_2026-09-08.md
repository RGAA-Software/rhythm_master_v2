## 已经存在的能力

- Windows Studio 的分类节点、连线、参数/表达式、撤销、纹理与数值节点预览；
  组件内部编辑、公开参数、拆包、跨工程用户组件库已经实现。
- 音乐文件和 Windows 实时音频输入、频段/响度/onset/BPM 特征；
  波形、关键帧、局部时间、段落包络、暂停/跳转/循环及单曲作品绑定。
- 图像/视频纹理、合成、模糊、噪声、位移、轮廓、反馈/拖尾；
  点阵、CPU 粒子/流场、2D 物理；基础模型、场景、相机、基础 PBR 和方向光。
- 保存/恢复、携带媒体的运行包、Windows 播放与音画导出；
  Android 内置 32 个现有场景，界面选效果、音乐播放及场景横竖屏切换。

这些是可运行的创作基础。数量和单项闭环不等于已经达到成熟创作软件的完整程度。

## 本地 TiXL 的具体参考入口

以下已查看源码正文，可用作后续聚焦复用的起点；并非已导入模块：

- `Core/Animation/VDefinition.cs`：独立入/出插值、切线角度、权重、断开切线及影响范围；
  对照我们的三种插值，能明确下一步曲线契约应补什么。
- `Editor/Gui/Windows/TimeLine/TimeClips/ClipTimingEditor.cs`：片段/源区间和速度编辑；
  区分作品时间、媒体源时间与片段时间，避免另建竞争播放时钟。
- `Editor/Gui/Windows/Variations/SnapshotCanvas.cs`：多节点快照和混合操作入口；
  我们需要的是可操作的参数快照流程，而非继续增加静态预设记录。
- `Core/DataTypes/ParticleSystem.cs`：GPU buffer 形式的粒子状态；
  我们当前 CPU PointCloud 的渲染不应被表述为同等通用 GPU 管线。

3D 实现继续以既定 Godot 参考计划为主；媒体仍只用 FFmpeg。
每次实际提取源码时沿用现有来源、许可和适配记录规则，保留平台/模块边界。

## 接下来按功能交付

用户进一步要求聚焦渲染差距后，具体顺序统一到
[渲染能力与实施规划](rendering_capability_roadmap.md)，取代本节此前的线性五项顺序。
创作任务均保留，但不让完整多轨编排成为改善画面的前置条件：

1. **下一步**：短验证现有 Windows/Android 后端的实例化与计算能力，然后交付 GPU
   粒子/批量实例节点和真实音乐驱动作品。
2. **渲染主线**：浮点/线性颜色和可采样深度 → 纹理材质/灯光/阴影 → 程序化几何
   与受约束 shader 扩展；每批均有可编辑工程和可播放结果。
3. **创作控制穿插**：第一批作品先复用现有绑定/组件，再补曲线切线、快照/混合、
   宏控件；随后事件/Cue、片段源区间和多轨媒体仍沿用统一时间。
4. **内容持续交付**：随新能力扩展组件、浏览和宏控件，完成基础 50 + 高级 50；
   按结构、动态、音频响应和可编辑性验收，不以换色或横竖版重复计数。
5. **Android 同步**：各共享能力按实测设备能力落地，补 Player 参数/转场；
   覆盖安装、内置效果直接选择，短时中断/恢复检查随功能进行。

步骤有依赖但不是互相隔绝的长阶段：每个可交付增量及时接入 Studio 和目标 Player。
先完成已授权核心创作功能；任意脚本、原生插件 SDK、设备追踪、投影融合和全部
硬件协议不是因为竞品具备就自动展开的任务。Apple 仍是最后的平台移植，通信开发
仍后置；透明原生后缓冲仍为最后待定功能。

**长时间测试统一放到功能完成后的集中验收。** 当前保留受影响目标增量编译、
关键逻辑回归、短时真实音乐/实机验证；卡顿、崩溃与资源错误随功能修复。
不在每个增量反复跑 30 分钟、数小时或热稳定测试。已完成的长稳记录保留。
