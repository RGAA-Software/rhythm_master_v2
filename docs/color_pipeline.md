# 纹理精度与颜色流程

R2 的内部浮点合成使用 RGBA16F；显示和当前 FFmpeg 视频导出仍为 SDR。
浮点精度不代表 HDR 显示、HDR 视频编码或自动判断颜色空间。

## 编排约定

- 原有图片、视频和二维颜色节点按原来的 sRGB 数值工作。进入线性合成前，使用
  `texture.linearize`。它先解除预乘，对 RGB 做 sRGB 解码，再按原 alpha 预乘。
- 原生三维光照和按线性数值创作的粒子颜色直接进入线性流程，不重复解码。
- 在线性区间使用浮点精度完成曝光、加法合成、模糊。最后通过 `texture.display`
  选择曝光与 Reinhard 高光压缩或裁剪，再编码为 sRGB。显示转换只做一次。
- `output.texture` 不隐式改变颜色。作品的最终显示节点应输出 RGBA8，供 Studio、
  Player 和 SDR 导出共享。中间节点预览是数值预览，不自动猜测线性/显示编码。
- 数据纹理（例如线性深度）不能按颜色做 sRGB 解码。精度属性只描述存储格式，
  不改变数据含义。

## 精度与兼容

纹理生产节点提供继承输入、RGBA8、RGBA16F 三种精度。继承规则为：任意有效
纹理输入为浮点则输出浮点，否则 RGBA8。线性解码默认浮点，显示转换默认 RGBA8。
反馈的循环输入不能决定首次分配，需显式选择浮点；可控拖尾继续使用其浮点历史。
旧工程缺少精度属性时仍使用 RGBA8，保留原先的高光裁剪和颜色外观。

渲染目标缓存同时匹配尺寸与精度。精度变化会重新分配；模糊的各级中间目标保持
指定精度，半径为零时也遵守显式格式转换。浮点加法合成累加 RGB，alpha 使用覆盖率
合并，避免 alpha 大于 1 干扰后续解除预乘。RGBA8 的旧加法行为保持兼容。

## 验证

Windows D3D11 和 Android Adreno 650 GLES 3.1 的实际 GPU 读回已覆盖：

- 半透明像素的 sRGB 解码与编码往返，alpha 不参与 gamma 转换。
- 4 倍白色经曝光再乘 2、浮点模糊，最后 Reinhard + sRGB 输出约 242/255。
  若任何中间步骤裁剪到 1，该结果不会成立。
- 浮点加法的透明覆盖率，以及原有 GPU 粒子与实例化回归。
- 运行时精度继承、强制转换、缓存复用、零半径模糊和旧属性缺省兼容。

GPU 像素用例位于 `src/rhythm_render/tests/color_pipeline_gpu.cpp`；运行时用例位于
`src/runtime/tests/color_runtime_tests.cpp`。传递函数参考 GLM，Reinhard 实现参考 TiXL；
原始源码、具体修订、MIT 声明及适配范围见 `provenance/color_pipeline.json`。

可编辑实例“频谱星云”使用两组浮点粒子、线性柔光、背景解码与最终 SDR 映射。
24 节点版本已通过真实音乐驱动和 120 帧带音频 MP4 导出/解码测试，包含重复导出
逐帧一致性、音频连续性、静音差异与取消。场景数量不计作视觉品质验收。

## 导出在途帧约束

本机 D3D11 的浮点作品在三个 GPU 读回同时在途时，重复运行会出现少量原始帧的
红色通道 1 LSB 差异；有损编码会放大后续帧的差异。禁用纹理复用不能消除它。
将 GPU 在途图像限制为一帧后，恢复纹理复用并移除诊断插桩，逐帧一致性测试通过。
因此当前离线导出在前一图像读回完成后才推进下一次图求值；编码线程仍异步运行。
这项约束不改变实时 Player 的渲染节奏。底层驱动/后端差异来源尚未进一步归因，
重新启用多图像在途必须重过浮点作品的重复导出检查。

证据：`out/color-export-final.log`、`out/color-nebula-tests.log`、
`out/dof-android-probe.log`；原始诊断产物仅保留在忽略的 `out/` 中。
